### Компоненты включенные в логирование

Для реализации эффективного логирования системы с учётом трейсинга и мониторинга, важно собирать следующие **типы логов** и разделять их по уровням важности (INFO, WARN, ERROR). Логи должны содержать как минимальную информацию для простого анализа, так и подробности для глубокой диагностики. В идельной реализации логи должны быть структурированными и представлены в JSON формате.

### **Типы логов для сбора:**

#### **1. Логи работы с заказами:**

* **Описание:** Логи, связанные с созданием, изменением и обработкой заказов.
* **Данные для логирования (INFO):**

  * Время события
  * Идентификатор покупателя (user_id)
  * Номер заказа (order_id)
  * Статус заказа (например, "создан", "в обработке", "отправлен")
  * Технология/система, которая обработала заказ (например, MES или Shop API)

#### **2. Логи работы с 3D-моделями:**

* **Описание:** Логи загрузки и обработки 3D-моделей для заказов.
* **Данные для логирования (INFO):**

  * Время загрузки/обработки
  * Идентификатор заказа
  * Размер модели (например, количество полигонов)
  * Время обработки модели

#### **3. Логи работы с RabbitMQ (Messages Queue):**

* **Описание:** Логи отправки и получения сообщений через RabbitMQ.
* **Данные для логирования (INFO):**

  * Время события
  * Идентификатор сообщения
  * Очередь, через которую прошло сообщение
  * Статус обработки сообщения (например, "успешно доставлено", "ошибка")

#### **4. Логи работы с CRM:**

* **Описание:** Логи операций с клиентами в CRM.
* **Данные для логирования (INFO):**

  * Время события
  * Идентификатор клиента
  * Описание действия (например, "обновление информации о клиенте", "создание нового клиента")
  * ID запроса или сессии

#### **5. Логи для API запросов:**

* **Описание:** Логи запросов и ответов от API (Shop API, CRM API, MES API).
* **Данные для логирования (INFO):**

  * Время запроса
  * HTTP метод (GET, POST, PUT, DELETE)
  * URL запроса
  * Идентификатор пользователя (user_id), если применимо
  * Статус ответа (например, 200, 400, 500)

#### **6. Логи работы с БД (Shop DB, MES DB):**

* **Описание:** Логи операций с базами данных, включая запросы и ошибки.
* **Данные для логирования (INFO):**

  * Время события
  * Тип запроса (SELECT, INSERT, UPDATE, DELETE)
  * Таблица, с которой был выполнен запрос
  * Время выполнения запроса

---

### **Уровни логирования:**

#### **1. Уровень INFO** (Основные события, которые не требуют немедленного вмешательства, но полезны для понимания работы системы.)

* Пример: создание заказа, успешная обработка 3D-модели, успешное выполнение запроса в БД.

#### **2. Уровень WARN** (Предупреждения, которые требуют внимания, но не являются критичными.)

* Пример: запрос к базе данных выполняется дольше ожидаемого времени (например, более 5 секунд), большая нагрузка на сервер, повторяющиеся неудачные попытки.

  **Данные для логирования (WARN):**

  * Время события
  * Описание проблемы (например, "время обработки запроса превышает норму")
  * Причина предупреждения

#### **3. Уровень ERROR** (Ошибки, требующие немедленного внимания и возможной отладки.)

* Пример: сбой при обработке 3D-модели, ошибка в RabbitMQ, проблемы с базой данных, недоступность API.

  **Данные для логирования (ERROR):**

  * Время события
  * Тип ошибки (например, ошибка подключения, ошибка 500 на сервере)
  * Идентификатор запроса, если имеется
  * Стек вызовов ошибки или описание проблемы

#### **4. Уровень DEBUG** (Технические детали, полезные для разработчиков в процессе отладки.)

* Пример: Детальная информация о внутренних процессах, входных данных, промежуточных вычислениях.

  **Данные для логирования (DEBUG):**

  * Время события
  * Входные и выходные данные (если это не нарушает конфиденциальности)
  * Промежуточные вычисления

### Мотивация

Логирование необходимо внедрить в системы «Александрит» для того, чтобы повысить прозрачность работы платформы, сократить время на расследование инцидентов и обеспечить стабильность обработки заказов при растущей нагрузке. В отличие от трейсинга (который помогает исследовать цепочки запросов), **логи дают базовый, быстрый доступ к информации о работе сервисов, ошибках, событиях и поведении пользователей**. Это фундамент для поддержки и аналитики.

Ниже представлены ключевые причины, почему логирование необходимо включить в архитектуру в первую очередь.

---

**1. Ускорение расследования инцидентов (MTTR — Mean Time To Repair)**

Сейчас команда тратит много времени на выяснение причин:

* «куда пропал заказ»,
* «почему MES не рассчитал стоимость»,
* «почему CRM не получила сообщение из RabbitMQ»,
* «почему API-партнёра не получил ответ».

Логи событий позволяют:

* видеть историю обработки конкретного заказа,
* находить момент сбоя,
* оценивать влияние смежных систем.

Без логов проблему иногда невозможно воспроизвести — особенно если она проявилась ночью или у внешнего партнёра.

**Показатели, на которые влияет:**

* MTTR (сокращение времени устранения аварий)
* Количество инцидентов, доведённых до понимания первопричины (RCA completeness)

---

**2. Снижение числа просроченных заказов**

Контроль жизненного цикла заказа в логах позволяет:

* фиксировать задержки в CRM/MES,
* понимать, что расчёт стоимости в MES занял 30 минут вместо нормативных 3,
* видеть, что заказ «завис» в очереди RabbitMQ,
* выявлять медленные запросы в DB, блокирующие обновление статусов.

**Показатели, на которые влияет:**

* Количество просроченных заказов
* Количество потерянных заказов

---

**3. Улучшение качества поддержки и сокращение нагрузки на менеджеров**

Менеджеры CRM сейчас вынуждены вручную искать причину задержек заказа, что занимает время и ухудшает клиентский опыт.

Логи позволят:

* быстро объяснять клиенту, что происходит с заказом,
* передавать техподдержке чёткие данные,
* увидеть, что заказ задерживается не из-за менеджера, а из-за системной проблемы.

**Показатели, на которые влияет:**

* Среднее время ответа поддержки
* NPS (индекс потребительской лояльности)

---

**4. Выявление деградаций систем до жалоб клиентов**

Логирование ошибок, таймаутов, падения соединений, повторных попыток отправки сообщений позволит:

* видеть рост ошибок API заранее,
* замечать проблемы с соединениями RabbitMQ и Postgres,
* фиксировать частые ошибки в загрузке 3D-моделей.

Это даёт возможность реагировать до того, как ошибка станет массовой.

**Показатели:**

* Error rate
* Количество аварийных ситуаций

---

**5. Повышение информационной безопасности и контроля действий сотрудников**

Некоторые операции в CRM и MES критически важны и должны иметь аудит:

* смена статуса заказа,
* принятие заказа оператором,
* отмена заказа,
* изменение данных клиента,
* пересчёт стоимости в MES вручную.

Логи позволяют контролировать эти операции и уменьшить риски злоупотреблений или ошибок персонала.

**Показатели:**

* Количество событий небезопасных действий
* Успешность внутреннего аудита

---

#### **Какие системы следует логировать в первую очередь и почему**

Внедрить логирование сразу везде — невозможно. Поэтому приоритеты такие:

---

**1. Shop API — ПЕРВЫЙ приоритет**

**Почему:**

* точка входа заказов,
* высокая нагрузка,
* ошибки напрямую видит клиент,
* влияет на продажи и UX.

Логи здесь дают максимальное улучшение качества и скорости диагностики.

---

**2. MES API — ПЕРВЫЙ приоритет**

**Почему:**

* самая проблемная часть: расчёты 2–30 минут,
* частые таймауты и «зависания»,
* критично для создания заказа.

Большинство жалоб связано именно с этой системой.

---

**3. CRM API — ВТОРОЙ приоритет**

**Почему:**

* CRM формирует цепочку обработки заказа,
* много интеграций с парнёрами,
* без логов невозможно понять, почему заказ «не создан».

---

**4. RabbitMQ — ВТОРОЙ приоритет**

**Почему:**

* узкое место интеграции между CRM и MES,
* возможны «застревания» сообщений,
* влияет на SLA всей цепочки.

---

**5. Shop DB и MES DB — ТРЕТИЙ приоритет**

**Почему:**

* логи БД нужны для расследования сложных проблем
* основная ценность — логирование запросов API и логика приложений

Логи с БД — важное дополнение, но не первый слой диагностики.

### Предлагаемое решение

Для реализации логирования предлагается использовать ELK-стек.

**Реализация логирования с использованием ELK-стека**

**1. Архитектурные изменения: что внедрить и как это работает**

**Компоненты, которые необходимо добавить (все новые элементы — красным на схеме):**

1. **Filebeat/Fluent Bit (агенты логирования)**

   * Устанавливаются на каждый сервер/контейнер:

     * Shop API
     * CRM API
     * MES API
     * CRM
     * MES
     * RabbitMQ
     * Shop DB, MES DB (Postgres)
   * Ответственны за сбор файлов логов или stdout (если контейнеры).

2. **Logstash**

   * Централизованный компонент обработки логов.
   * Выполняет парсинг JSON, нормализацию полей, обогащение данными (например, service.name).
   * Фильтрация чувствительных данных.

3. **Elasticsearch**

   * Хранение логов.
   * Создание отдельных индексов под каждый сервис.

4. **Kibana**

   * UI для поиска, визуализации логов и настройки дашбордов.

---

**2. Какие системы подключаем к логированию (приоритеты)**

**В первую очередь:**

1. **MES API** — источник самых дорогих проблем (30-минутные расчёты, зависания).
2. **CRM API** — заказы не создаются, жалобы B2B клиентов.
3. **Shop API** — витрина, B2C-пользователи.

**Во вторую очередь:**
4) **CRM и MES UI** — важны, но не критичны.
5) **RabbitMQ** — для трассировки провалов интеграций.
6) **Базы данных** — техническое логирование (длительные запросы, блокировки).

---

**3. Как реализовано логирование**

**Шаги внедрения**

**Шаг 1: стандартизация формата логов**

* JSON-формат.
* Обязательные поля для всех сервисов:

  ```
  timestamp
  level
  service.name
  environment
  request.id / trace.id
  user.id (если есть)
  order.id (если есть)
  message
  error.stacktrace (если есть)
  duration_ms
  ```

**Шаг 2: внедрение агентов логирования (Filebeat)**

Агент:

* собирает локальные логи или Docker-stdout,
* отправляет через TCP/HTTP → Logstash.

**Шаг 3: настройка Logstash**

* Парсинг JSON.
* Фильтры:

  * удаление токенов авторизации,
  * анонимизация e-mail, телефон → hash,
  * обогащение service.name, env.

**Шаг 4: Elasticsearch**

* Индексация.
* Индекс-шаблоны:

  ```
  shop-api-logs-*
  crm-api-logs-*
  mes-api-logs-*
  mes-logs-*
  crm-logs-*
  rabbitmq-logs-*
  postgres-logs-*
  ```

**Шаг 5: Kibana**

* Дашборды:

  * Ошибки по сервисам
  * Длительные операции
  * Зависшие заказы
  * Ошибки интеграций
  * Проблемы RabbitMQ

---

#### **4. Политика безопасности для логов**

**4.1 Доступ к логам**

*Кто имеет доступ:*

| Роль                 | Доступ                                       |
| -------------------- | -------------------------------------------- |
| Поддержка            | Только к бизнес-логам (shop/crm/mes)         |
| Backend-разработчики | Доступ ко всем логам                         |
| DevOps               | Полный доступ (администраторы ELK)           |
| Аналитики            | Только к агрегированным, обезличенным данным |

*Инструменты безопасности:*

* LDAP / Active Directory интеграция.
* RBAC в Elastic Security.
* Audit logging — фиксировать, кто смотрел какие логи.

---

**4.2 Работа с чувствительными данными**

Чувствительные данные:

* ФИО
* телефон
* email
* адрес
* цена изделия
* 3D-файлы или их ссылки
* токены API
* JWT

**В Logstash необходимо:**

* удалять токены:

  ```
  mutate { remove_field => ["auth.header", "jwt"] }
  ```
* хешировать e-mail/телефон:

  ```
  mutate { update => { "user.email" => "%{user.email.hash}" } }
  ```

---

#### **4.3 Политика хранения логов**

*Сроки хранения:*

* **API-сервисы:** 30 дней
* **RabbitMQ:** 14 дней
* **DB-логи:** 14–30 дней
* **ИТ-безопасность:** 90 дней
* **Аудит логов доступа:** 180–365 дней

*Размеры данных:*

* Примерно 0.5–2 ГБ логов в сутки, зависит от нагрузки.
* Хранение в виде отдельных индексов на сервис.

### Cистема анализа логов

**Преобразование логирования в аналитическую платформу логов**

После внедрения ELK-стека логирование само по себе даёт только хранилище данных. Чтобы система стала действительно полезной для бизнеса, необходимо выполнить дополнительные мероприятия: внедрить алертинг, интеграцию с метрическими данными и построение поисковых сценариев для расследований.

---

**1. Настройка алертинга в Elasticsearch/Kibana**

**1.1 Создать набор бизнес-алертов**

Эти алерты должны фиксировать ситуации, когда страдает клиентский опыт.

**Алерты для B2C-витрины (Shop API)**

* Резкий рост ошибок 500 за последние 5 минут.
* Отсутствие заказов в течение 10 минут при нормальном уровне трафика.
* Среднее время ответа выросло в 3 раза.

**Алерты для B2B API (расчёт стоимости изделий)**

* Ошибка создания заказа в CRM после прихода сообщения из MES.
* Расчёт стоимости > 30 минут.
* Исключительные ошибки в логах MES API.

**Алерты для RabbitMQ**

* Dead Letter eXchange (DLX) очереди растут быстрее, чем обрабатываются.
* Сообщения не забираются более N минут.
* Очередь стала "idle" — значит потребитель не работает.

**Алерты для CRM и MES**

* Нет новых изменений статусов заказов X минут.
* Ошибки в обработке статуса заказа.
* «Зависшие» заказы: нет движения по статусам.

---

**2. Поиск аномалий**

**2.1 Аномально высокая нагрузка на API**

Примеры:

* Превышение нормального уровня RPS в 5–10 раз.
* Резкое увеличение количества запросов с одного IP.
* Подозрительные шаблоны трафика (DDoS, бот-атаки).

**Почему важно:**
MES API и Shop API страдают от перегрузок — аномалии позволяют поймать проблему до отказа.

---

**2.2 Аномалии в RabbitMQ**

* Появление сообщений в DLX быстрее, чем их обрабатывают.
* Время жизни сообщений в очереди превышает норму.
* Потребитель исчез (Worker down).
* Скачок ошибок ACK/NACK.

**Почему важно:**
Очереди — сердцевина интеграции CRM ↔ MES. Задержки → потерянные заказы.

---

**2.3 Аномалии по заказам (бизнес-анализ)**

* За минуту появилась непропорционально большая серия заказов — возможно:

  * интеграционный баг,
  * дубляж заказов,
  * повторные отправки из-за ошибок,
  * мошенническая активность.

* Нескольким пользователям одновременно приходит ошибка при расчёте стоимости изделия.

* В CRM перестали появляться новые заказы.

---

**3. Корреляция логов разных систем**

Чтобы находить цепочки проблем, необходимо:

**3.1 Добавить request.id / trace.id во все логи**

Это позволит:

* видеть всю цепочку: Shop API → CRM API → RabbitMQ → MES API → MES,
* отслеживать где «сломалась» обработка заказа,
* измерять end-to-end time.

**3.2 Логи должны содержать бизнес-идентификаторы**

* order.id
* customer.id
* model.id
* mes.task.id

Это позволит обнаруживать:

* зависшие заказы,
* дублирующиеся заказы,
* пропавшие сообщения.

---

**4. Создание аналитических дашбордов**

ELK должен включать:

* дашборды производительности API,
* дашборды ошибок,
* RabbitMQ queue overview,
* дашборды заказов (статусы, SLA, зависшие),
* дашборды для B2B-партнёров (доступность обработки заказов).

---

**5. Интеграция с системой уведомлений**

Уведомления должны идти в зависимости от критичности:

**Куда отправляем:**

* Slack / Telegram — операционная команда
* Email — поддержка
* Jira — автоматически создаваемые инциденты
* PagerDuty/«Звонилка» — при критических отказах

**Когда:**

* сервис недоступен,
* очередь сообщений заполнена,
* резкий рост ошибок,
* потеря связи CRM ↔ MES,
* отклонения в SLA заказов.

---

**6. Политика реакций на инциденты**

- Если превышен порог RPS → блокировать подозрительные IP или включить rate limiting.
- Если DLX очередь растет → автооткрытие инцидента + уведомление разработчикам интеграции.
