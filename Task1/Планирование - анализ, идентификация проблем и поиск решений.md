# Планирование: анализ проблем и поиск решений

## Контекст и цели

В разделе описано текущее положение компании и техническое состояние IT инфраструктуры.

### Бизнес-контекст

- Компания "Алекссандрит" предоставляет услуги изготовления ювелирных украшений.
- Заказы поступаю через Онлайн-магазин и API MES системы.
- Заказчиками являются частные лица и сторонние продавцы ювелирных изделий.
- Через месяц после открытия API компания потеряла несколько крупных контрактов из-за проблем с заказами.
- Растет количество жалоб от клиентов на просроченные заказы.

### Технический контекст

- MES и CRM взаимодействуют друг с другом через RabbitMQ.
- Открыто API MES системы, который MES использует для расчёта стоимости изделия.
- Онлайн-магазин отделен от MES системы.
- Расчет стоимости модели в среднем занимает 2-3 минуты, но сложная модель может обрабатываться до 30 минут.
- Заказы в среднем растут на 100 в месяц.
- Производственные мощности позволяют справиться с заказами и могут обеспечить двукратный рост.
- Долгая загрузка первой страницы MES при работе Операторов с сервисом.
- На главной странице MES препятствует фильтр по статусам и пагинация.

## Предлагаемые **решения**

### Решение для [3 - Отсутствие кэширования]

**Проблема:**
Постоянная нагрузка на базы банных, запрос одинаковых данных все это увеличивает время ответа.

Критические точки для кэширования:

- Shop API: Каталог товаров, цены
- MES API: Справочники операторов, статусы
- CRM API: Данные клиентов, история заказов

**Предлагаемое решение:**
Внедрение Redis для кэширования

**Почему**: Быстрый способ улучшить отзывчивость сервиса, сразу снизит нагрузку на БД на 60-80%

**Эффект**: Улучшение отклика API, снижение нагрузки на базы

---

### Решение для [7 - Отсутствие API Gateway]

**Проблема:**
Rate limiting распределен по сервисам, сложная маршрутизация, не позволяет масштабировать сервисы.

**Предлагаемое решение:**
Внедрение API Gateway (nginx как пример).

**Почему**: Это основа для управления API, разделения трафика и внедрения политик безопасности и rate limiting. Это также позволит в будущем легко добавлять новые сервисы и изменять маршрутизацию.

**Эффект**: Возможность независимого масштабирования и развития.

---

### Решение для [1 - Жёсткая связность сервисов через общую БД]

**Проблема:**
Сервисы Shop API и CRM API работают с одной базой данных (Shop DB), что приводит к жёсткой связности между ними. Это создаёт сложности при миграции, расширении и обновлении сервисов.

Критические точки для декомпозиции:

* Shop API: Доступ к данным о товарах и заказах.
* CRM API: Доступ к данным о клиентах и их истории заказов.

**Предлагаемое решение:**
Разделение данных между сервисами. Использование подхода с микросервисами и отдельными базами данных для Shop API и CRM API.

**Почему:**
Декомпозиция сервисов и их данных позволяет улучшить масштабируемость, повысить гибкость при обновлениях и снизить зависимость между сервисами. Каждый сервис может иметь собственную модель данных, что упрощает миграцию и обновления.

**Эффект:**
Повышение отказоустойчивости, улучшение масштабируемости и возможности независимых обновлений сервисов.

---

### Решение для [4 - Единая точка отказа — RabbitMQ]

**Проблема:**
Все асинхронные коммуникации между сервисами проходят через один брокер сообщений (RabbitMQ), что создаёт единую точку отказа. Если брокер выходит из строя, все сервисы, зависящие от него, перестают функционировать.

Критические точки:

* Shop API: Зависимость от сообщений о заказах.
* CRM API: Зависимость от уведомлений о клиентах.

**Предлагаемое решение:**
Использование кластеризации RabbitMQ или переход на более отказоустойчивые решения, такие как Kafka, которые имеют встроенную поддержку кластеризации и failover.

**Почему:**
Кластеризация и failover обеспечивают отказоустойчивость в случае сбоев одного из брокеров. Kafka и NATS также обеспечивают более высокую доступность.

**Эффект:**
Увеличение отказоустойчивости системы и снижение вероятности остановки сервисов из-за сбоя брокера сообщений.

---

### Решение для [5 - Синхронная обработка тяжёлых операций]

**Проблема:**
Синхронная обработка тяжёлых операций, таких как расчёт цен в MES API, блокирует потоки и замедляет работу всей системы, особенно при высокой нагрузке.

Критические точки:

* MES API: Сложные и ресурсоёмкие операции по расчёту цен и изделий.

**Предлагаемое решение:**
Перевод тяжёлых операций на асинхронный режим или использование очередей задач для делегирования сложных вычислений в фоновом режиме.

**Почему:**
Асинхронная обработка позволяет разгрузить основной поток и избежать блокировки, повышая пропускную способность и производительность системы.

**Эффект:**
Ускорение обработки запросов и повышение отзывчивости API.

---

### Решение для [2 - Неподходящий выбор брокера сообщений]

**Проблема:**
RabbitMQ является потенциально узким местом сервиса: отсутствует репликации и ограниченная производительность.

**Предлагаемое решение:**
Миграция критичных событий на Kafka

**Почему**: RabbitMQ менее масштабируемый по сравнению с Kafka, сложнее обеспечить высокую производительность при большом объёме данных.

**Эффект**: Появляется возможность event sourcing и replay (повторного запроса)

---

### Решение для [6 - Проблемы с базами данных]

**Проблема:**
Отсутствие репликации для чтения и наличие архитектуры с двумя независимыми базами данных приводит к проблемам с консистентность данных и нагрузкой на мастер-узлы.

Критические точки:

* Shop DB: Основная БД для хранения данных о товарах и заказах.
* MES DB: БД для расчётов и обработки данных о производственных процессах.

**Предлагаемое решение:**
Внедрение репликации для чтения и улучшение консистентность данных между базами данных.

**Почему:**
Репликация для чтения позволит разгрузить мастер-узел и ускорить выполнение запросов на чтение. Это также обеспечит большую гибкость в распределении нагрузки.

**Эффект:**
Уменьшение нагрузки на мастер-узлы, улучшение доступности и консистентности данных.

---

### Решение для [8 - Неэффективная работа с 3D-файлами]

**Проблема:**
Загрузка и обработка больших 3D-файлов блокирует потоки, что замедляет работу системы. Также отсутствие сжатия и оптимизации файлов приводит к их большому объёму и дополнительной нагрузке.

Критические точки:

* 3d files storage: Хранение и обработка больших 3D-файлов.

**Предлагаемое решение:**
Внедрение сжатия 3D-файлов перед загрузкой и использование асинхронной обработки для файлов, чтобы не блокировать основной поток.

**Почему:**
Сжатие снизит нагрузку на хранилище и ускорит процесс загрузки файлов. Асинхронная обработка позволит избежать блокировки потока.

**Эффект:**
Ускорение обработки 3D-файлов и снижение нагрузки на систему.

---

### Решение для [9 - Отсутствие read-моделей]

**Проблема:**
Отсутствие read-моделей и архитектуры CQRS (Command Query Responsibility Segregation) ограничивает возможности для эффективного чтения данных и увеличивает нагрузку на базовые таблицы.

Критические точки:

* Shop DB: Запросы для отображения товаров.
* MES DB: Запросы для получения информации о производственных процессах.

**Предлагаемое решение:**
Внедрение CQRS и создание отдельных read-моделей для чтения данных.

**Почему:**
CQRS позволяет разделить нагрузку на чтение и запись данных, что повышает производительность и уменьшает вероятность блокировки базы данных.

**Эффект:**
Ускорение работы с данными, снижение нагрузки на основные таблицы, повышение масштабируемости.

---

### Решение для [10 - Отсутствие мониторинга]

**Проблема:**
Отсутствие мониторинга приводит к незнанию текущего состояния системы, отсутствуют метрики и алерты, что затрудняет выявление и решение проблем с производительностью и доступностью.

Критические точки:

* Все сервисы: Shop API, CRM API, MES API.

**Предлагаемое решение:**
Внедрение системы мониторинга и логирования, таких, как Prometheus и Grafana, для отслеживания метрик и алертинга по ошибкам.

**Почему:**
Мониторинг позволяет своевременно выявлять проблемы с производительностью и доступностью, что способствует быстрой реакции на инциденты и улучшению стабильности системы.

**Эффект:**
Улучшение видимости системы, своевременное реагирование на проблемы, повышение стабильности и доступности сервисов.

---

### Решение для [11 - Ограниченная масштабируемость]

**Проблема:**
Текущая архитектура ограничивает возможности горизонтального масштабирования, создавая риски потери данных и ухудшения производительности при увеличении нагрузки.

Критические точки:

* Shop API: Обработка запросов к каталогу товаров.
* CRM API: Управление данными клиентов и заказами.

**Предлагаемое решение:**
Реализация подходов для улучшения горизонтальной масштабируемости, таких, как использование кластеризации сервисов и улучшение балансировки нагрузки.

**Почему:**
Горизонтальное масштабирование позволяет распределить нагрузку между несколькими инстансами, повышая отказоустойчивость и пропускную способность системы.

**Эффект:**
Увеличение производительности, снижение рисков потери данных и улучшение устойчивости системы к высокой нагрузке.

## Целевая архитектура

### Описание изменений

Основные цели изменений архитектуры заключается в:

- скорейшее устранение просрочки заказов и недовольств клиентов
- увеличение прибыли за счет новых клиентов
- не допустить потери контрактов
- обеспечить полную загрузку производства

В разделе "Предлагаемые решения" описаны основные проблемы и решения текущей архитектуры. Здесь представлена последовательность шагов для достижения целевой архитектуры.

1. Внедрение базового мониторинга.
   - Мониторинг даст текущие метрики, которые можно принять за точку отсчета. Это поможет в дальнейшем отслеживать эффект внедрения новых подходов и решений.

2. Внедрение кэширования.
   - Быстро реализуемое решение, которое снизит нагрузку на БД и увеличит отзывчивость сервиса.

3. Внедрение API Gateway.
   - Основа для всех последующих изменений. Позволяет управлять трафиком и потоками запросов, обеспечит бесшовную модернизацию сервиса.

Это 3 пункта не требуют больших затрат ресурсов и могут быть выполнены в первые полгода. При этом они сразу могут дать положительный результат - увеличить отзывчивость сервиса и ускорить переход заказов в производство.

Эти пункты необходимы, но недостаточны, чтобы справиться с нагрузкой. Требуется внедрение других решений с приоритетом 1.

### Преимущества и метрики

После реализации плана система будет иметь:

- **Снижение времени обработки заказов на XX%** - за счет кэширования и оптимизации API, что напрямую уменьшит просрочку заказов
- **Повышение доступности системы до 99.5%** - благодаря API Gateway и мониторингу, что предотвратит потерю контрактов из-за простоев
- **Увеличение пропускной способности на 40%** - что позволит обслуживать больше клиентов без деградации производительности

**Метрики успеха:**

- **Время обработки заказа**: целевое 2 часа
- **Количество просроченных заказов**: целевое 5%
- **Доступность системы для клиентов**: целевая 99.5%
- **Время отклика интерфейса магазина**: целевое 1 секунда
- **Конверсия оформления заказов**: целевая 35%
- **Загрузка производственных мощностей**: целевая 85%
