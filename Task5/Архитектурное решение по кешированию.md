### Компоненты требующие кэшировния

Для начала определим критерии - кеширование имеет смысл, если:

* данные часто читаются и редко изменяются,
* API или подсистема тормозит под нагрузкой,
* операция дорогая по CPU / сети / диску,
* сервис создаёт каскадную нагрузку на другие сервисы.

Этим критериям соответствуют следующие компоненты системы.

* Кеширование в Internet Shop (Frontend, 3D editor)
* Shop API
* CRM API
* MES API
* CRM UI
* MES UI

### Мотивация

#### **1. Кеширование в Internet Shop (Frontend, 3D editor)**

**Что кешировать**

1. **Каталог товаров (список изделий, коллекции, категории)**

   * Меняется редко.
   * Запрашивается огромным количеством пользователей.

2. **Карточки товаров (описание, характеристики, цена без кастомизации)**

   * Почти статический контент.

3. **Результаты валидации 3D-моделей до отправки в MES**

   * Если клиент перезагружает страницу или отправляет тот же файл повторно.

**Зачем**

* Уменьшение нагрузки на Shop API -> снижает задержки.
* Улучшение UX -> мгновенная загрузка каталога.
* Снижение нагрузки на Shop DB -> уменьшение рисков деградации.

---

#### **2. Shop API - критично важно кешировать**

**Что кешировать**

1. **Каталог и справочники (товары, категории, атрибуты)**

   * Как и во фронте, это горячая точка.

2. **Промежуточные результаты расчётов, не зависящие от MES**

   * Например: базовая цена за грамм металла, коэффициенты, промо-настройки.

3. **Состояние заказа (если заказ не менялся последние X секунд)**

   * Чтобы не бить CRM и MES каждый раз.

**Зачем**

* Снятие нагрузки с CRM API и MES API.
* Ускорение основных пользовательских сценариев.

---

#### **3. CRM API - кешировать обязательно**

CRM - система, заваленная запросами от операторов и магазинов.

**Что кешировать**

1. **Карточка клиента** (ФИО, email, история последних заказов)
2. **Справочники CRM** (статусы, типы заказов, источники трафика)
3. **Список новых/активных заказов для операторов**

   * Это дергается *каждые несколько секунд* на панели оператора.

### **Зачем**

* Снижение нагрузки на CRM DB.
* Ускорение UI в CRM -> меньше жалоб от сотрудников.
* Предотвращение деградации, которая уже наблюдается.

---

#### **4. MES API**

Тут один из самых тяжелых участков системы.

**Что кешировать**

1. **Справочники MES**

   * список операторов, статусные модели, участки производства.

2. **Промежуточные результаты расчётов цен (если возможно)**

   * Например: материалы, коэффициенты не меняются часто.

3. **Статусы производственных заданий**

   * Они меняются редко, но читаются постоянно.

---

#### **5. MES (UI)**

**Большие жалобы:**

> «страница со списком заказов грузится очень долго»

**Что кешировать**

1. **Список заказов по статусам** (дашборд оператора)
2. **Пагинированные выборки заказов**
3. **Фильтры, наборы данных, агрегаты**
4. **Имя оператора + его заказы**

### Предлагаемое решение

Рассмотрим использование кэширования на стороне клиента.

Клиентское кеширование (браузер, CDN, ETag, Cache-Control) подходит для статичного контента: картинок, JS, CSS, публичных страниц каталога.

Но ключевые проблемы компании - не в клиентской отдаче фронтенда. Основные узкие места находятся:

* в API между MES/CRM и внешними партнёрами,
* в медленных расчётах стоимости (до 30 минут!),
* в пагинации и выдаче списков заказов для операторов в MES,
* в штормах нагрузки от партнёров,
* в RabbitMQ-интеграциях.

Эта часть нагрузки вообще не проходит через клиентский кеш.

Клиентское кеширование не решает ключевых проблем производительности, связанных с backend-инфраструктурой и межсервисными вызовами.

Поэтому выбираем кэширование на стороне сервера. Серверное кеширование улучшит ситуацию там, где существует:

* повторяемость запросов,
* высокая задержка вычислений,
* дорогие операции чтения,
* высокая нагрузка от сторонних пользователей API.

---

#### **MES (результат расчёта стоимости по 3D)**

**Паттерн:** Cache-Aside

**Почему:**

* Результат зависит только от содержимого 3D-файла -> можно безопасно кешировать по хешу файла.
* Расчёт дорогой; при попадании в Cache мы избегаем ненужных расчётов.
* Нужно защищаться от «штормов» однотипных запросов -> singleflight (первый запрос запускает расчёт, остальные ждут или получают заглушку).

**TTL:** долгое (7–30 дней) - в зависимости от бизнес-правил (если материалы/цены не меняются часто).

**Инвалидация:** при изменении прайса/материалов - MES публикует message в RabbitMQ -> слушатель инвалидирует/пересчитывает ключи.

**Почему не Refresh-Ahead / Write-Through:**

* Refresh-Ahead будет много тратить ресурсов на расчёты, которые никто не запросит.
* Write-Through невозможен, потому что MES - внешняя/чёрная коробка (мы не можем заставить её писать в наш кеш синхронно).

---

#### **Shop API (каталог, карточки товаров, справочники)**

**Паттерн:** Cache-Aside + client cache для статичных артефактов.

**Почему:**

* Каталог читается часто и меняется редко -> хорошая цель как для Cache-Aside, так и для Refresh-Ahead.

**TTL:**

* каталог/карточка: 1h–24h (в зависимости от частоты обновлений),

**Инвалидация:** при изменении товара Shop API отправляет событие в RabbitMQ -> слушатель вызывает `DEL`/обновление в Redis.

**Почему Write-Through не нужен:** можно, но сложнее; Cache-Aside проще и даёт гибкость.

---

#### **CRM API / MES UI (операторские дашборды)**

**Паттерн:** Cache-Aside с очень коротким TTL + push-инвалидация через события.

**Почему:**

* Операторы часто рефрешат списки заказов; чтения частые, записи редкие (изменение состояние заказа).
* Короткий TTL (10–20s) обеспечивает свежесть.
* Push-инвалидация: при изменении статуса сервис публикует событие -> кэши соответствующих страниц инвалидируются.

---

#### **Invaldation / Consistency**

* **Event-driven invalidation**: при write-операции сервис публикует событие в RabbitMQ -> отдельный worker слушает и инвалидирует ключи. Это критично для согласованности.
* **Versioned keys**: добавлять `version` (например, `shop:item:<id>:v<catalog_version>`) если массовая инвалидация нужна быстро.

### Диаграмма последовательности операции чтения и изменения статуса заказа

[Операция чтения списка заказов и запись об изменении статуса заказа](./Order_pass_sequence.puml)

**Короткие пояснения (что показано и почему)**

Для чтения списка заказов использован Cache-Aside: Shop API сначала обращается в Redis; при промахе — в Postgres и затем наполняет Redis. Это снижает нагрузку при частых чтениях (операторы/пагинация).

Для записи/смены статуса показан сценарий, когда MES обновляет статус (MANUFACTURING_STARTED) и публикует событие в RabbitMQ. Cache invalidator (worker) — подписчик очереди — удаляет соответствующие ключи в Redis, чтобы предотвратить рассинхронизацию (а также при необходимости инициирует обновление кэша).

Добавлены заметки с примерами ключей кеша и TTL для наглядности.

В диаграмме выделены все сущности, которые участвуют в кешировании: Redis (cache store), Shop API (reads/writes cache) и Cache Invalidator (инвалидация и опциональное обновление кэша). Также MQ используется как механизм подписки на события, обеспечивающий event-driven invalidation.

### Cтратегия инвалидации кеша

**Комбинированная стратегия: инвалидация по ключу + временная (TTL)**

#### Почему:

1. **Статусы заказов меняются нечасто**, но происходят критичные апдейты (MES, CRM, Shop API).
   → Нужно *гарантированно* сбрасывать кэш после изменения статуса → **инвалидация по ключу**.

2. **Списки заказов читаются очень часто**, отличаются по фильтрам (status=NEW, status=PACKAGING).
   → Даже при инвалидации по событию возможны ситуации, когда что-то не доехало или не все ключи были сброшены → **TTL даёт самовосстановление кэша**.

3. **TTL защищает от устаревшего кэша**, если что-то пойдёт не так в MQ/Invalidator.

4. **Инвалидация по ключу через событие MQ** идеально ложится на текущую архитектуру.

---

#### Почему другие стратегии хуже

* Только TTL:
  * Может держать устаревший статус заказа несколько секунд.
  * Критично для производственных систем MES/CRM.

* Только инвалидация по ключу:
  * Если Invalidator упадёт или MQ-сообщение потеряется, кэш останется вечным.
  * TTL страховка от ошибок.

* Программная инвалидация:
  * Лишний код и повышенная сложность.
  * Риск того, что кто-то забудет инвалидировать связанную коллекцию.

* Полная инвалидация:
  * Уничтожит производительность.
  * Ненужна в микросервисной системе с большими потоками чтения.
