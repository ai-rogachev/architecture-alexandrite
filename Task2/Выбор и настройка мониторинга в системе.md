# Выбор и настройка мониторинга в системе

## Мотивация

Внедрение мониторинга на текущем этапе развития компании необходимо для:

- Повышения удовлетворенности клиентов.
  - В текущей архитектуре нет маркерных показателей производительности сервиса, на основе которых можно было бы принимать решения об изменении той или иной части системы. Жалобы клиентов и операторов являются субъективными показателями, которые сложно оценить и они не дают понимния какая часть архитектуры требует доработки. Внедрение мониторинга повысит лояльность клиентов.
- Ускорения обработки и выполнения заказа.
  - Учитывая недозагруженность производства, необходимо понять какая часть архитектуры замедляет переход заказа к операторам. Мониторинг позволит выявить узкие места. В последующем это поможет ускорить обработку заказа и избежать просрочки. Тем самым компания сможет обрабатывать больше заказов.
- Получения ценных бизнес-инсайтов.
  - Благодаря накопленной статистики появится возможность оценить заказы оформленные через API. Это позволит принимать обоснованные бизнес решения о развитии компании.
- Более быстрого решения проблем и повышения надёжности системы.
  - В текущей архитектуре есть узкие места, проблемы в которых можут привести к остановке сервиса. Это повлечет за собой недополученную прибыль и недовольных клиентов. Мониторинг позволит быстро обнаружить проблему, определить ее корень и быстро восстановить работоспособность.

## Выбор подхода к мониторингу

### Части системы и соответствующие подходы мониторинга

**Подсистема**:
Internet Shop, CRM, MES (UI)

**Подход мониторинга**:
RED - Rate(скорость), Errors(ошибки) и Duration(продолжительность)

**Причина использования подхода**:
RED позволяет отслеживать важные показатели для пользователя:

- Rate - частота операций менеджеров и запросов пользователей
- Errors - ошибки API или пользовательского ввода
- Duration - задержки CRUD-операций, аналитики, отчётов

---

**Подсистема**:
Shop API, CRM API, MES API

**Подход мониторинга**:
4 золотых сигнала - Задержка (Latency), Трафик (Traffic), Ошибки (Errors), Насыщенность (Saturation).

**Причина использования подхода**:
Для работы с API метод 4-х золотых сигналов позволяет отслеживать основные показатели работы сервисов:

- Latency - Задержки при оформлении заказов, задержки при проведении операций с заказами. Задержка запросов может означать перегрузку серверов или недостаточную масштабируемость.
- Traffic - Количество запросов к каталогу, количество запросов к данным клиентов, количество запросов о сстоянии заказа. В случае большого объёма данных необходимо отслеживать, насколько эффективно API справляется с нагрузкой.
- Errors - Ошибки при оформлении заказов, ошибки поиска товаров, ошибки расчета цены заказа. КОличество ошибок свидетельствует о проблемах серверов или инфраструктуры и позволяет оперативно их выявлять и исправлять.
- Saturation - Загрузка процессора и памяти, заполнение очередей сообщений, использование соединений с базой данных. Позволяет выявить задержки или потеря данных из-за исчерпания серверных мощностей.

---

**Подсистема**:
Messages Queue (RabbitMQ)

**Подход мониторинга**:
USE - Utilization (Использование), Saturation (Насыщенность) и Errors (Ошибки)

**Причина использования подхода**:
Это подход, который хорошо работает для мониторинга ресурсных ограничений и эффективности работы очередей сообщений, а также для выявления ошибок в системе.

- Utilization - Процент использования системных ресурсов для работы RabbitMQ. Это включает в себя использование процессора, памяти и диска, а также сетевых соединений.
- Saturation - Пороговые значение, насколько близка система к своему пределу ресурсов. Это позволяет понять, насколько система загружена и готова ли она к новым запросам или сообщениям.
- Errors - Количество и тип ошибок, которые происходят при работе RabbitMQ. Ошибки могут происходить на разных уровнях, включая отказ в доставке сообщений или проблемы с доступом к очередям.

---

**Подсистема**:
Shop DB, MES DB (Postgres)

**Подход мониторинга**:
4 золотых сигнала - Задержка (Latency), Трафик (Traffic), Ошибки (Errors), Насыщенность (Saturation).

**Причина использования подхода**:
Для работы с API метод 4-х золотых сигналов позволяет отслеживать основные показатели работы баз данных:

- Latency - Время ответа на запросы для получения информации о товарах, заказах, клиентах.
- Traffic - Количество запросов, поступающих от API или других сервисов, например, на получение данных о товарах и заказах.
- Errors - Ошибки, связанные с нарушением ограничений (например, попытки вставки данных, нарушающие уникальные индексы или внешние ключи).
- Saturation - Пороговые значение, насколько близка база данных к своему пределу ресурсов. Может включать использование процессора, памяти, диска и подключения к базе данных.

## Метрики и части системы

Для каждой из подсистем мы будем отслеживать определённые метрики, которые соответствуют подходам мониторинга (RED, 4 Golden Signals, USE). Далее описаны причины для выбранных метрик, а также необходимость ярлыков для них.

Вот полный скорректированный список метрик, распределённых по подсистемам с соответствующими подходами мониторинга:

---

### **Подсистема: Internet Shop, CRM, MES (UI)**

**Подход мониторинга**: **RED** (Rate, Errors, Duration)

- **Number of requests (RPS) for internet shop API**
Измеряет количество запросов в секунду, направляемых к API интернет-магазина, что важно для мониторинга производительности сервиса.

- **Number of requests (RPS) for CRM API**
Измеряет количество запросов в секунду, направляемых к CRM API, что важно для анализа загрузки API и оптимизации.

- **Number of requests (RPS) for MES API**
Измеряет количество запросов в секунду, направляемых к MES API. Важно для оценки нагрузки на API, особенно при производственных операциях.

- **Response time (latency) for shop API**
Важна для измерения времени отклика на запросы, что позволяет контролировать скорость работы интернет-магазина.

- **Response time (latency) for CRM API**
Измеряет время отклика на запросы CRM, что важно для оптимизации производительности системы взаимодействия с клиентами.

- **Response time (latency) for MES API**
Время отклика для MES API важно для мониторинга задержек в производственных процессах.

---

### **Подсистема: Shop API, CRM API, MES API**

**Подход мониторинга**: **4 Golden Signals** (Latency, Traffic, Errors, Saturation)

- **Number of HTTP 500 for shop API**
Ошибки HTTP 500 показывают сбои на сервере и могут свидетельствовать о проблемах с инфраструктурой.

- **Number of HTTP 500 for CRM API**
Ошибки 500 в CRM API указывают на сбои в сервисах, связанных с клиентскими данными.

- **Number of HTTP 500 for MES API**
Ошибки на сервере MES API могут нарушить производственные процессы, что критично для мониторинга.

- **CPU % for shop API**
Отслеживает загрузку процессора, что важно для оценки способности API обрабатывать запросы.

- **CPU % for CRM API**
Анализ загрузки процессора для CRM API помогает понять, насколько эффективно работает система в периоды пиковой нагрузки.

- **CPU % for MES API**
Важно отслеживать процессорные ресурсы для MES API, так как аналитика и обработка данных требуют вычислительных мощностей.

- **Memory Utilisation for shop API**
Помогает отслеживать использование памяти в Shop API и выявить потенциальные утечки памяти.

- **Memory Utilisation for CRM API**
Важно отслеживать использование памяти в CRM API, чтобы предотвратить перегрузку и утечку памяти.

- **Memory Utilisation for MES API**
Контроль за памятью необходим для обеспечения стабильности MES API, особенно при сложных вычислениях и анализе данных.

- **Number of simultaneous sessions for shop API**
Счётчик одновременно активных сессий помогает понять, насколько сильно нагружена система и сколько пользователей одновременно взаимодействуют с интернет-магазином.

- **Number of simultaneous sessions for CRM API**
Важно отслеживать количество активных сессий CRM API, чтобы понимать текущую нагрузку на систему взаимодействия с клиентами.

- **Number of simultaneous sessions for MES API**
Метрика помогает контролировать нагрузку на MES API, особенно в периоды пиковых нагрузок в производственном процессе.

---

### **Подсистема: Messages Queue (RabbitMQ)**

**Подход мониторинга**: **USE** (Utilization, Saturation, Errors)

- **Number of dead-letter-exchange letters in RabbitMQ**
Позволяет отслеживать сообщения, которые не могут быть обработаны и попадают в dead-letter queue. Это помогает выявить проблемы с доставкой сообщений.

- **Number of messages in flight in RabbitMQ**
Оценка количества сообщений, находящихся в процессе обработки. Это помогает анализировать текущую нагрузку на очередь и её производительность.

---

### **Подсистема: Shop DB, MES DB (Postgres)**

**Подход мониторинга**: **4 Golden Signals** (Latency, Traffic, Errors, Saturation)

- **Number of connections for shop db instance**
Количество подключений к базе данных позволяет отслеживать нагрузку на БД и понять, если база данных перегружена.

- **Number of connections for MES db instance**
Аналогично метрике для Shop DB, позволяет контролировать количество подключений и их влияние на производительность базы данных MES.

- **Memory Utilisation for shop db instance**
Важно следить за использованием памяти в базе данных Shop DB, чтобы избежать утечек памяти или излишней нагрузки.

- **Memory Utilisation for MES db instance**
Отслеживание использования памяти в базе данных MES необходимо для предотвращения перегрузки памяти в пиковые моменты.

- **Size of shop db instance**
Контроль за размером базы данных помогает планировать её масштабирование и оценивать её рост.

- **Size of MES db instance**
Размер базы данных MES важен для оценки её производительности и потенциальных узких мест.

## Показатели насыщенности

Для разных подсистема целесообразно определить разные показатели насыщенности. Далее представлены выделенные подсистемы и соответстуюшие им показатели.

### **Подсистема: Shop API, CRM API, MES API**

Показатели насыщенности:

- Использование CPU (%)
  - Пороговое значение: 80-85% загрузки.
  - Причина использования:
    - Высокая загрузка процессора может привести к значительному замедлению отклика сервиса или привести к ошибка.
  - Действия при превышении порога:
    - Оповестить ответственного.
    - Автоматически масштабировать API сервисы, если возможно.
    - ИЛИ Завести тикет для команды DevOps с просьбой определить причины нагрузки и увеличить ресурсы при необходимости.

- Использование RAM (% Memory Usage)
  - Пороговое значение: 80%
  - Причина использования:
    - Если приложение или сервис использует более 80% доступной памяти, система может начать использовать своп, что приведёт к значительным задержкам.
  - Действия при превышении порога:
    - Установить уведомления для мониторинга роста потребления памяти.
    - Автоматически масштабировать API сервисы, если возможно.
    - Добавить больше оперативной памяти на существующие инстансы или добавить новые экземпляры.

- Количество открытых соединений с базой данных (Database Connections)
  - Пороговое значение: 90% от максимального количества допустимых соединений.
  - Причина использования:
    - При достижении этого порога система рискует не принимать новые запросы, что приведёт к сбоям и перегрузке.
  - Действия при превышении порога:
    - Установить уведомления для мониторинга роста потребления памяти.
    - Настроить повторное соединение с базой данных для освобождения соединений.
    - Уточнить возможность применения одной из стратегий масштабирования БД.

### **Подсистема: Messages Queue (RabbitMQ)**

Показатели насыщенности:

- Количество сообщений в очереди (Queue Length)
  - Пороговое значение: Если очередь не может обработать более 80% своих сообщений в установленное время (например, более 1 часа).
  - Причина использования:
    - Очереди, которые переполняются, могут привести к задержкам и потере сообщений, что критично для целостности данных.
  - Действия при превышении порога:
    - Оповестить ответственного.
    - Завести тикет для команды, чтобы проверить логи на наличие возможных ошибок, которые приводят к переполнению.
    - Автоматически масштабировать очередь, если возможно.

- Использование процессора и памяти в RabbitMQ (CPU % / Memory Usage)
  - Пороговое значение: 80% CPU или памяти.
  - Причина использования:
    - Превышение этого порога может привести к потере сообщений или к тому, что сервер RabbitMQ станет менее отзывчивым.
  - Действия при превышении порога:
    - Оповестить ответственного.
    - Проверить, существуют ли подписчики, которые избыточно загружают очередь.

### **Подсистема: Shop DB, MES DB (Postgres)**

Показатели насыщенности такие же как и для API:

- Использование CPU (%)
  - Пороговое значение: 80-85% загрузки.
  - Причина использования:
    - Высокая загрузка процессора может затруднить выполнение запросов, что приведёт к задержкам в ответах.
  - Действия при превышении порога:
    - Оповестить ответственного.
    - Автоматически масштабировать БД, если возможно.
    - Завести тикет для команды разработчиков с предложением оптимизировать запросы (например, с помощью индексов или изменений в SQL).

- Использование RAM (% Memory Usage)
  - Пороговое значение: 80%
  - Причина использования:
    - Если приложение или сервис использует более 80% доступной памяти, система может начать использовать своп, что приведёт к значительным задержкам.
  - Действия при превышении порога:
    - Установить уведомления для мониторинга роста потребления памяти.
    - Проверить запросы, использующие большое количество памяти, и оптимизировать их.
    - Добавить больше оперативной памяти на существующие инстансы или добавить новые экземпляры.

- Количество открытых соединений с базой данных (Database Connections)
  - Пороговое значение: 90% от максимального количества допустимых соединений.
  - Причина использования:
    - При достижении порога новых соединений не удастся установить, что приведёт к сбоям в работе приложений.
  - Действия при превышении порога:
    - Установить уведомления об превышении лимита соединений с базой данных.
    - Провести анализ для поиска утечек соединений и устранить их.
    - Рассмотреть возможность использования пулов соединений, чтобы оптимизировать количество активных подключений.
