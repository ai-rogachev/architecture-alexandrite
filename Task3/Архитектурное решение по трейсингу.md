#### Список данных

Общие атрибуты для всех span:

| Атрибут          | Описание                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| **trace_id**     | Уникальный идентификатор для всей трассировки. Позволяет связывать все шаги процесса (заказа). |
| **span_id**      | Идентификатор конкретной операции в рамках трассировки.                                        |
| **parent_id**    | Идентификатор родительского спана (для иерархической связи).                                   |
| **service.name** | Название сервиса, который создал данный спан. Это поможет понять, где происходит ошибка.       |
| **environment**  | Среда (например, prod/stage), в которой работает сервис.                                       |
| **request_id**   | Уникальный идентификатор для HTTP-запроса (для связи с логами и диагностикой).                 |
| **timestamp**    | Время начала и окончания работы спана (время выполнения операции).                             |

Атрибуты, специфичные для заказа:

| Атрибут                 | Зачем                                      |
| ----------------------- | ------------------------------------------ |
| **order_id**            | Чтобы увидеть путь конкретного заказа      |
| **user_id / client_id** | Чтобы понять чья операция                  |
| **session_id**          | Для мульти-запросов фронтенда              |
| **operation_type**      | create/update/calc/status-change           |
| **business_status**     | статус заказа (pending, confirmed, failed) |

### Мотивация

Исходя из текущей ситуации компании, критично важно быстро выявлять и устранять сбои информационной системы.
Каждое замедление или выход строя какого-либо компонента приводит к потере прибыли компании.
Поэтому внедрение трейсинга позволяет сделать систему прозрачной:
видно, где именно произошёл сбой, почему произошла деградация скорости и какой сервис
стал "бутылочным горлышком". Это сократит время простоя и решения по оптимизации.

Теперь подробнее:

- Быстрая диагностика проблем

Сегодня на разбор инцидента уходит часы — поиск логов, сравнение временных меток, опрос разных команд.
Трейсинг сокращает время поиска причины проблемы.

---

- Прозрачность бизнес-операций и контроль заказов

Каждый заказ проходит через цепочку сервисов.

Трейсинг даёт возможность смотреть:

* где заказ завис
* какое действие заняло слишком много времени
* были ли ретраи
* на каком этапе возникла ошибка

Менеджеры получают **более точную аналитику**, а техподдержка — меньше обращений, потому что ошибки находят заранее.

---

- Оптимизация производительности и планирования

Трейсинг показывает,

* какие сервисы перегружены
* где долгие SQL-запросы
* какие запросы вызывают самую большую задержку цепочек

Компания может принимать решения о:

* масштабировании
* перераспределении ресурсов
* рефакторинге конкретных узких мест

Это позволяет **экономить инфраструктурные расходы**.

### Предлагаемое решение

Для реализации трейсинга прелгагается пройти следующие шаги.

#### Шаги для реализации трейсинга

1. **Выбор технологии для трейсинга**
   Для трейсинга распределённых систем часто используют решения, такие как:

   * **Jaeger** (с open-source поддержкой от CNCF) — это популярное решение для распределённого трейсинга.
   * **Zipkin** — ещё одно распространённое решение, схожее с Jaeger.
   * **OpenTelemetry** — современный подход для мониторинга, который поддерживает трейсинг и метрики и имеет интеграцию с Jaeger и Zipkin.

   В данном случае, используем **Jaeger** для трейсинга, так как это один из самых широко применяемых инструментов с хорошей поддержкой и интеграцией с другими компонентами.

2. **Интеграция с компонентами**
   Все системы и сервисы, которые участвуют в процессе обработки заказов, должны быть настроены на отправку трейсинговых данных:

   * **Shop API**
   * **CRM API**
   * **MES API**
   * **RabbitMQ** (для очередей сообщений)

3. **Что нужно добавить/доработать**
   Для внедрения трейсинга в текущую инфраструктуру необходимо выполнить следующие задачи:

   * **Интеграция с Jaeger** на каждом из сервисов. В каждом API и сервисе нужно будет внедрить клиента Jaeger или использовать OpenTelemetry.
   * **Конфигурация трассировки для RabbitMQ** — необходимо интегрировать с Jaeger для отслеживания очередей сообщений.
   * **Установка агентов Jaeger** (или аналогичных) на сервисах и компонентах системы, таких как серверы API и RabbitMQ.

4. **Обработка и хранилище данных**
   Трейсинговые данные будут поступать в **Jaeger Collector**, который будет собирать и агрегировать данные, затем отображать их в интерфейсе **Jaeger UI** или в интегрированном дашборде (например, с Grafana).

---

#### Архитектура и компоненты

* **Shop API**, **CRM API**, **MES API**: Все сервисы будут интегрированы с Jaeger для передачи трейсинговых данных.
* **RabbitMQ**: Интеграция с Jaeger для отслеживания сообщений в очередях.
* **Jaeger Agent/Collector**: Агент собирает и отправляет данные о трассировках, Collector обрабатывает и сохраняет эти данные.
* **Jaeger UI**: Для визуализации трассировок и анализа задержек и ошибок.

#### Дополнительное задание

1. Концепция и реализация

Для мониторинга процесса прохождения заказа мы будем использовать стандартный стек, который отлично интегрируется с Jaeger — Prometheus (для сбора и хранения метрик) и Alertmanager (для обработки и отправки уведомлений).

Этапы реализации:

- Извлечение метрик из трейсинга (Trace-to-Metrics):

   Мы будем использовать Jaeger Query (или специализированный компонент, такой как OpenTelemetry Collector с процессором метрик) для периодического запроса данных трассировки из Jaeger DB.

   На основе этих запросов будут генерироваться ключевые метрики, отражающие выполнение бизнес-процесса, например:

      Trace Duration SLO: Процент заказов, которые уложились в допустимое время (например, от создания до присвоения оператору).

      Error Rate: Частота сбоев (трасс с ошибками/статусами HTTP 5xx) для ключевых этапов процесса.

      Latency: Медианное (P95/P99) время выполнения критически важных операций (например, Shop API: /order/create).

- Хранение и агрегация:

   Полученные метрики передаются в Prometheus — это база данных временных рядов, которая агрегирует данные и позволяет строить сложные запросы.

- Алертинг:

   В Prometheus определяются правила оповещения (Alerting Rules). Например, ALERT OrderProcessingTimeTooHigh IF trace_duration_p95{operation="order_full_trace"} > 10s.

   При срабатывании правила Prometheus отправляет алерт в Alertmanager.

- Уведомление:

   Alertmanager отвечает за дедупликацию, группировку и маршрутизацию алертов, отправляя уведомления в соответствующие каналы (например, в Slack/Microsoft Teams для команды поддержки или на PagerDuty для критических инцидентов).

- Визуализация:

   Grafana подключается к Prometheus для создания дашбордов, которые наглядно показывают ключевые метрики процесса (например, график времени прохождения заказа по дням, количество ошибок).

### Компромиссы

С учётом положения компании «Александрит» и её архитектуры, трейсинг может не принести пользы в следующих случаях:

1. **Сложности с интеграцией старых систем (MES и CRM)**:

   * **Описание**: MES был куплен вместе с исходным кодом и может не поддерживать возможности для интеграции с системами трейсинга. Внедрение трейсинга в такой системе может потребовать значительных доработок, что увеличит стоимость и срок реализации.
   * **Причина, по которой трейсинг не будет полезен**: Система не была изначально спроектирована с учётом возможностей для мониторинга и трейсинга, а её устаревшая архитектура может усложнить внедрение современных методов слежения за производственными процессами.

2. **Нехватка инструментов для подробного мониторинга производственных операций**:

   * **Описание**: Производственная система (MES) и API взаимодействуют через RabbitMQ, однако интеграция с внешними системами и API не всегда прозрачна, и без трейсинга сложно понять, на каком именно этапе происходит задержка.
   * **Причина, по которой трейсинг не будет полезен**: Без встроенных средств для отслеживания всех взаимодействий через очереди сообщений, внедрение трейсинга будет требовать сложных изменений, что увеличивает риск ошибок и затрат на техническую доработку.

3. **Неоптимальные проблемы с производительностью из-за недостаточной масштабируемости API**:

   * **Описание**: Когда компания начала принимать заказы от других продавцов через API, система не была подготовлена к большому количеству запросов, что привело к снижению производительности и увеличению времени отклика.
   * **Причина, по которой трейсинг не будет полезен**: Проблема заключается не только в недостаточной видимости процессов, но и в том, что текущая архитектура системы не масштабируется должным образом. В таких случаях трейсинг не решит проблему с производительностью без доработки API и масштабирования инфраструктуры.

4. **Невозможность мониторинга взаимодействий на всех уровнях из-за отсутствия единого подхода**:

   * **Описание**: Поскольку множество процессов завязаны на старых компонентах (CRM, MES), а новые сервисы, такие как API, плохо интегрированы, будет сложно обеспечить единую картину для трейсинга всех этапов — от API-запросов до производственных процессов.
   * **Причина, по которой трейсинг не будет полезен**: Отсутствие централизованного подхода к трейсингу в текущей архитектуре и необходимости переписывать или модифицировать несколько устаревших компонентов делает внедрение трейсинга крайне затратным.

### Аспекты безопасности

**Предотвращение несанкционированного доступа снаружи (External Security)**

Основные усилия направлены на то, чтобы предотвратить любой доступ к данным трассировки из общедоступной сети Интернет.

- Jaeger UI и Jaeger Collector должны располагаться в закрытом сегменте сети (VPC/Intranet). Доступ из внешней сети (Интернет) к ним должен быть полностью заблокирован. Сотрудники могут получить доступ к UI только через корпоративный VPN или из офисной сети.

- Порты, которые используются для приёма трейсинговых данных (Jaeger Collector), должны быть закрыты на внешнем периметре и доступны только для внутренних сервисов и агентов.

**Меры безопасности внутри компании (Internal Security)**

- Доступ к веб-интерфейсу Jaeger UI возможен только через единую систему аутентификации (SSO/LDAP) компании. Внедряется контроль доступа на основе ролей (RBAC): доступ разрешён только ограниченному кругу лиц (например, с ролями "DevOps", "SRE" или "Поддержка"), чья работа требует анализа трассировок.

- Все сервисы (Shop API, CRM API, MES API) должны использовать TLS/SSL-шифрование (HTTPS) при отправке спанов на Jaeger Collector. В идеале, использовать mTLS (взаимное TLS) для аутентификации самих сервисов перед Collector'ом.
